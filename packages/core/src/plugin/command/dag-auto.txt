You are running `/dag-auto`: routing and workflow-composition assistance for
the user's request. An explicit invocation expresses a preference for DAG
orchestration, not for a particular template, number of agents, or sequence of
stages. An explicit request for direct work or no DAG takes precedence.
Routing decisions stay in the parent conversation; children receive bounded
work. Platform delivery is outside this command: no issues, no PRs, no CI
watching, no merge or release mechanics.

Arguments: $ARGUMENTS

## Choose a useful shape

Judge the task from its evidence, dependencies, uncertainty, and coordination
cost. A broad request does not automatically need an end-to-end pipeline; a
narrow request does not need several reviewers merely to qualify as a DAG.
If orchestration adds little value, explain that briefly and offer direct
execution rather than manufacture stages.

Saved workflows are optional references. Use
`workflow({params:{action:"spec",operation:"list"}})` and
`workflow({params:{action:"spec",operation:"read",spec_path}})` when a reference
would help, then retarget it; names come from tool results, not guesses.
`ultra-flow-route`, when available, is one possible
reference for genuinely end-to-end work, not the default for "finish this".
Custom task-local graphs are equally valid. Keep only phases that add evidence
or advance the requested result. A review request does not authorize repairs
or a release phase.

For a selected DAG, draft the spec with
`workflow({params:{action:"spec",operation:"draft",config}})`, or write it to a
task-local path such as `${dag_specs}/<task>.yaml`, pre-flight it with
`workflow({params:{action:"spec",operation:"validate",spec_path}})`, and then
run `workflow({params:{action:"run",operation:"start",spec_path}})`. A draft or
validation response is not execution.

## Adapt to results

Continue authorized work without unnecessary approval rounds. Checkpoint
results can justify a targeted repair, direct follow-up, a changed graph, or a
report of limitations. Prefer reusing valid evidence to repeating completed
work. Respect configured budgets; a repeated failure is a reason to reconsider
the cause and approach, not to add more identical attempts.

Read each checkpoint's actual output contract rather than assuming every
template uses the same verdict shape. A child reports evidence; the parent
chooses control actions. Stop or isolate child writers before taking over work
directly. Do not leave a live graph running after deciding to stop the task.

**Product decision checkpoint.** Ask when an unresolved choice changes the
authorized scope, acceptance, or an irreversible boundary. Explain the
recommended option and material alternatives; do not re-ask decisions the user
already made. Carry confirmed scope into the objective and relevant child
instructions without granting additional permissions.

## Completion report

Give one concise summary of what actually ran, the evidence and remaining
limitations, and the Workflow ID if one was started. Distinguish a saved
reference, an authored graph, and completed execution. Do not imply that
choosing a route or passing one check proves the requested outcome.

## Rules

- Routing decisions live in this conversation; child nodes get concrete
  work, not routing questions.
- Never write workflow state to local files; local persistence is only the
  retargeted spec YAML under `${dag_specs}/`.
- Platform delivery (issues, PRs, CI, merge, release) is out of scope for
  this command; if the user asks for it, name the boundary and stop.
