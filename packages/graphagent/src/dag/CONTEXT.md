# Workflow Orchestration Context

Workflow Orchestration turns one user objective into one durable DAG. Its model-facing tool accepts saved or file-backed custom workflows and recommends heuristic composition from reusable Blocks. Low-level Nodes remain available when a Block route cannot express the objective.

## Glossary

| Term                     | Meaning                                                                                                                                                                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workflow Source          | An in-memory object used by trusted internal callers or a YAML document supplied to runtime and release tooling. Model-authored graph actions use YAML through `spec_path`.                                                                       |
| Workflow Authoring Check | The side-effect-free source-to-graph boundary that parses, normalizes file compatibility, instantiates template inputs, decodes the action shape, compiles Blocks, applies the selected validation profile, and returns diagnostics or a Prepared Workflow Graph.               |
| Prepared Workflow Graph  | A strictly decoded and compiled graph that passed the requested authoring checks and is ready for a runtime mutation.                                                                                                                             |
| Workflow Control         | The shared owner-checked boundary that applies pause, resume, step, cancel, complete, replan, extend, recover, extend_timeout, and retarget requests through `Dag`, with one rejection vocabulary and the post-failure parking protocol.          |
| Workflow Route           | A complete Block or Node composition selected for one objective. It may be custom, saved, or assembled heuristically.                                                                                                                             |
| Orchestration Router     | The product-owned parent guidance (the `dag-auto` built-in skill plus the always-on workflow-routing description) that qualifies an objective and selects one Workflow Route. Reference contracts live in the hidden `dag-*` skills.                                                                                                                    |
| DAG Guidance Skill       | One of the six built-in `dag-*` skills (auto/blocks/nodes/recovery/patterns/policy). `dag-auto` is promoted to the `/dag-auto` command; the other five are hidden reference-only and load by name.                                                                                    |
| Block Composer           | The Orchestration Router decision that selects the smallest Block graph justified by current evidence.                                                                                                                                            |
| Decision Checkpoint      | One parent-owned confirmation for unresolved user choices that materially change behavior, scope, acceptance, or an irreversible boundary.                                                                                                        |
| Reporting Checkpoint     | A `report_to_parent: true` node with dependents; its dependents must gate on its output via `condition`, or it must be a reporting leaf.                                                                                                          |
| Template Inputs          | The `inputs` a start document declares (`string`, `number`, `boolean`, or `array`; no `default` means required). `run.start { spec_path, inputs }` fills them: the Workflow Authoring Check replaces `{{name}}` placeholders of declared inputs in the parsed document, before strict decoding, and leaves every other `{{name}}` for the runtime's node bindings. |
| Live Gate                | A reporting checkpoint of the live workflow that enumerates a "carry on" verdict (`ACCEPT` for a review decision, `PASS` for a verification) and has not settled. A block of an extend fragment that depends on one is gated on that verdict, as a dependent of an in-document review block is. |
| Workflow Brief           | The recommended route, scope, acceptance evidence, assumptions, risks, and material alternatives presented at a Decision Checkpoint.                                                                                                              |
| Block                    | A reusable high-level orchestration capability such as explore, plan, debug, coding, verify, or review. Blocks compile into Nodes.                                                                                                                |
| Fan-out Writer           | A writer whose `fan_out` dependency's `packages` output decides, at admission, whether it runs as parallel package writers joined by an aggregator under its id or as itself. The package writers and the aggregator (`generated_helper: "aggregate"`) take the writer's `required`, so a required writer block fails the workflow at the one package that fails. |
| Compose Block            | A block of kind `compose` (or a node whose `worker_type` is a composer): a composer agent plans, the engine expands. `worker_type` names the composer and is required. The Workflow Authoring Check compiles it, with the effective agent catalog at hand, into a Split Node and an Expansion Slot (`DagCompose.compileNodes`); a composer that is missing, is not a composer, or has nothing it can expand into (`dispatch` holds no public read-only agent, or `fallback` is not one) is a validation error naming the agent and the cause. Under the portable profile there is no catalog, so the block stays one node and the check does not judge the composer; the environment profile every start, extend and replan runs under compiles it, and reports a compose block it had no composer catalog to compile (`DagCompose.uncompiledBlocks`), because run as one node it would not expand. |
| Split Node               | `<id>--split`: the composer, asked for a plan. Its `output_schema` is the plan schema generated from the composer's contract (`DagCompose.planSchema`: `agent` is an enum of the dispatchable agents, at most `dag.compose.max_children` items, `split` only for `recursive_split`). It is optional, so a failed plan still reaches the slot. The same function plus `checkPlan` is how the runtime checks the plan again before it expands it. |
| Expansion Slot           | `<id>`, the node a compose block's dependents bind to, carrying `expand: "<id>--split"`. It is the join node already written (composer, join prompt, the artifact the composer declares, `required` and `report_to_parent` as authored) and depends on the split node alone. The marker is persisted in the node definition and is not a field any model-writable schema has. At admission, once its split node has settled, the scheduler never spawns it as authored: `DagComposeExpansion` replaces it, in one `Dag.extend`, with the plan's children and the Join Node under the same id. |
| Join Node                | The Expansion Slot after expansion: the same definition under the same id, so every binding to it stays, without `expand`, depending on the plan's children, reading the plan and each child by node id, and carrying `join` (persisted): the split node, per item the child node, its agent and whether the item's work is required, `nested` for an item that became a nested expansion (its node is the nested slot, which becomes the nested join node, and its agent the composer that joins it), `unsplit` with the reason for an item that asked to be split again and ran as one worker, and why the expansion degraded when it did. A child is `<id>--<item>`, a read-only node (`workspace_writes: "deny"`) that sees only its own instruction; it is `required` only when the item is and the block is, so a required item of an optional block is found missing by the join's admission check, not by the scheduler. Before it is spawned the loop asks `DagComposeExpansion.admitJoin`, which reads the children by the node ids `join` holds and refuses without asking a model: `compose_required_missing` when a required item has no result, `compose_no_results` when no child has one (the fallback worker of a degraded expansion included); the node's own `required` then decides what the failure costs. |
| Fallback Worker          | `<id>--fallback`: the one worker, the composer's `fallback` agent, that takes the whole task as the block's author wrote it when a plan cannot be expanded: missing, invalid or empty, an agent no longer expandable, no room in the subtree, a taken id, or a graph the ceiling refuses. It is as required as the block, and the reason is kept as `join.degraded`, written into both prompts and logged. When the ceiling refuses even the fallback, the slot fails with `compose_capacity`; when the composer itself can no longer be used (gone, or nothing public and read-only left to expand into), it fails with `compose_unavailable` and there is no fallback either. Expanding never fails or parks the workflow. |
| compose_subtree          | The persisted mark `{ root, depth }` on every node an expansion generated: children, nested split nodes and slots, fallback workers. The author's own nodes (the block's split node, its slot and the join node the slot becomes) do not carry it. `root` is the id the top-level slot had when it was expanded and only groups one block's subtree (a key, not a reference); `depth` is the level of the plan the node takes part in, a top-level plan being 1. `DagCompose.positionOf` reads the depth and what is left of `dag.compose.max_subtree_nodes` from the persisted graph alone, so planning the same graph again after a crash or a recovery writes the same ids and siblings share the quota in the order they are expanded. A recursive composer's item with `split: true` becomes a nested split node and slot while `max_depth` and the quota allow, and runs as one worker, with the reason in `join.items[].unsplit`, when they do not. |
| Compose Failure Classes  | `compose_capacity` and `compose_unavailable` fail the slot at expansion (above); `compose_required_missing` and `compose_no_results` fail the join node at admission (above). All four are `error_class` values of an ordinary failed node, so the node's own `required` decides what the failure costs and coverage lists them as failed nodes. |
| Writer                   | A node that can change the workspace (`DagBlocks.isWriterNode`): a `coding` or `prototype` block, or a node whose worker is not a read-only profile and whose effective `workspace_writes` is not `deny`. The generated fan-out aggregator is never one. One definition feeds the plan-agent gate, the `dag.permission: "readonly"` gate, the write-conflict check, and default isolation. A `coding` or `prototype` block that leaves `required` out compiles to `required: true` (D9: failed code fails the workflow at the writer, not later at a verification that read a placeholder); an explicit `required: false` keeps its optional semantics, and every read-only block keeps its own default. |
| Write Conflict           | A request that would put, or for a retarget move, an unisolated writer into a workspace where another live workflow still has an unfinished unisolated writer. `workflow start` and the `DagControl` extend, replan, recover, and retarget prechecks refuse it (`DagWriteGuard`). |
| Default Isolation        | The engine's choice of workflow-level `isolation: "worktree"` for a strict workflow whose writers are not all ordered, from a clean git checkout with a commit, when the document binds no workspace or isolation. |
| Node                     | A low-level durable unit of child-agent work with dependencies, prompt input, policy, and output contract.                                                                                                                                        |
| Model Tier               | `advanced` or `standard` of `dag.model`: where a node's default model comes from. `DagConfig.tierOf` decides it from the node's role, never from `required` (which is failure semantics). Advanced: a review or `auditor` worker; `plan`, `verify`, `synthesize` and review blocks; a `debug` block's diagnosis; a composer's split node, expansion slot and join node. Standard: writers (`coding`, `prototype`, a `fan_out` writer's package writers and aggregators), `explore` blocks, a `debug` block's evidence node, and the children an expansion planned (a join node's `join.items` names them). A node with no block and no such marker is hand-written and has no role: `required` takes the advanced tier, as before. |
| Prior Round              | The stored review round a block's `prior_round` continues; the engine resolves it into `prior_findings` keyed `<workflow_id>/<lane>/<index>` and the next `review_round`.                                                                         |
| Coverage Entry           | One deterministic node-level reason the caller did not see the whole picture: gate skip, abort, failure, serial fan-out fallback, budget pause, `not_examined`, unread result page, or review-loop stop. `inspect` and delivery render the same list. |
| Pause Reason             | The durable `workflow.pause_reason` recorded with `WorkflowPaused` (for example `budget_exhausted`). It describes only the current pause episode and is cleared by resume, terminal settlement, or replan.                                        |
| Display State            | The presentation-only node state derived from the raw status: a cancelled node displays as `cancelled`, a running escalation-pending node as `escalated`, otherwise the raw status. Raw `status` and `error_class` remain available to consumers. |
| Validation Profile       | `portable` checks source-contained structure without user environment state; `environment` additionally resolves live agents, prompt assets, and models.                                                                                          |
| Runtime Admission        | The READY/WAIVED gate for a deep workflow. It is a lifecycle policy after authoring, not another name for Workflow Authoring Check.                                                                                                               |
| Delivery                 | The single DAG delivery scheduler (`DagDelivery`) that admits durable wake batches and queued agent messages to an idle parent session. It owns the in-flight reservations and the wake-first/mailbox-second order, and registers as the `dag.delivery` inbox source (priority 5, `idle_only`) on the shared per-instance `SessionInbox`, which holds the single idle subscription. Delivery is event-driven: terminal and node events and `DagMessages.changed` nudge it, an idle transition retries a deferred admission, and the inbox's 30s tick (its scan lists unreported wakes, due paused reminders, and one mailbox ledger page per call) is the only periodic fallback. |
| DagMessages.changed      | The process-scoped PubSub stream of committed agent-mailbox changes (`queued`, `delivered`, `closed`). It is published after the outermost transaction commits, never on rollback, and is a notification only.                                      |
| Runner Lease             | One `dag_runner` row per workflow naming the engine process (`pid:nonce`) that drives it, with an epoch and an expiry (`DagLease` in core, `RunnerLease` in the loop; claimed before an adoption or a child session, renewed every 30 seconds, released when its workflow ends and at a clean exit; a lease found lost, by a failed renewal or by a spawn's re-read, is not evicted by the lease itself but handed to the Reconciler to judge; [ADR-0008](docs/adr/0008-runner-lease-and-write-fence.md)). Not the "DAG lease" that older prose and tests call the `ExclusiveRegistry` registration, which only keeps a goal off a session while its workflow runs. |
| DagTransact              | The core primitive `transact(dagID, token?, body)` that every `Dag` command changing an existing workflow runs in: one `BEGIN IMMEDIATE` transaction that fences on the token (when one is given), then guards, then publishes, and rolls everything back on failure. Event notification (`subscribe`, `all`, `listen`) follows the outermost commit and never happens on rollback. It is a required dependency of `Dag.layer` (4b-E): there is no unfenced fallback, every graph that builds `Dag`, a test harness included, provides a real one, and a command's body takes database work only, so nothing may park inside it ([ADR-0008](docs/adr/0008-runner-lease-and-write-fence.md), decision 3). |
| Runner Port              | The `Dag` service with a runtime entry's runner writes bound to its lease token (`RunnerPort.make` in `runtime/runner-port.ts`). A runner write is a command whose decision rests on the runner's own scheduling state (`nodeQueued`, `nodeStarted`, `nodeCompleted`, `nodeFailed`, `nodeSkipped`, `nodeTimeoutEscalated`, `nodeExtendTimeout`, `settleCompletion`, and the loop's own `pause`, `pauseForCheckpoint`, `extend`, `fail` and `failOrphan`, the orphan `pending` workflow's pending -> running -> failed in one transaction); everything a user, an agent or a policy asks for is an intent write and carries no token. A refused token (`StaleRunnerError`) never reaches a caller: the port evicts the workflow and fails the call with a transition rejection ([ADR-0008](docs/adr/0008-runner-lease-and-write-fence.md), decisions 4 and 5). |
| Reconciler               | The per-instance shell (`DagReconciler` in `runtime/reconciler.ts`) that settles who drives a non-terminal workflow: it observes one workflow (the row, directory ownership, the execution location, the lease row, the instance's runtime entry), asks `decide` for one action, runs it, and keeps at most one evaluation under way per workflow. It has two entries: `reconcile(dagID)` for the startup round and the 30-second renewal tick (the tick starts its round in a fiber of its own, one at a time, never waited for), where concurrent calls share one evaluation; and `reconcileAfter(dagID)` for the event triggers (a first wave on `WorkflowStarted`, a replan with no runtime entry, a session `Moved`, a lease found lost by a renewal or a spawn's re-read), which waits for an evaluation under way to end and evaluates once more, so its verdict never comes from state read before the event, and the calls that arrive during one wait share that re-evaluation. Every runtime entry is created by the adoption that an evaluation runs (`recoverWorkflow`, which reads the row again once it holds the claim), so the loop keeps no adoption reservation of its own. A clock watch fed by the tick and by every observation holds back the takeover of an expired lease after a clock jump. It retires the entry of a workflow that ended or was deleted (row 1: the cleanup, the lease give-back, the worktree settlement and the wake of the parent, the one routine `retireTerminal` that the `WorkflowTerminal` handlers run too, done once per entry by whichever reaches it first), which is what removes the entry of a workflow that another process ended, whose terminal event never reaches this process (the news is a lost lease found by a renewal or a spawn's re-read, or, when the lease row still names this runner because a control op needs no lease, the round, which looks after its scan of the live statuses at every entry the scan did not list). It also disposes of the orphan `pending` rows an older version left behind, after a 60-second grace period; the disposal is one runner command, `Dag.failOrphan` (`WorkflowStarted` and `WorkflowFailed` in one fenced transaction) ([ADR-0008](docs/adr/0008-runner-lease-and-write-fence.md), decision 6). |
| decide                   | The pure function `decide(observation)` in `runtime/reconcile-decide.ts` that returns the one action for an observation by the ten-row truth table of ADR-0008 decision 6 (`noop`, `retire`, `evict`, `fail-unrecoverable`, `defer`, `renew`, `terminalize-orphan`, `adopt`), first matching row wins; row 1 (the workflow is terminal or gone) is `retire` when the instance has an entry for it and `noop` otherwise. It reads and writes nothing; a new recovery policy is a new row in the table, not a new recovery path. |

## Invariants

- Block composition is the recommended authoring path and is selected heuristically from the objective; custom Blocks/Nodes remain supported.
- Workflow Authoring Check is the only raw source-to-Prepared Workflow Graph authority used by tool actions, CLI, generation, and packaging.
- Parsing, file-only compatibility, strict action decoding, Block compilation, and profile diagnostics are not reimplemented by callers.
- `portable` validation does not load user environment catalogs. `environment` validation reads current catalogs and verifies actual model availability.
- Workflow graph creation or replacement requires a valid Prepared Workflow Graph. A rejected live mutation may still publish durable `WorkflowPaused` through the Workflow Control parking path to park the existing graph.
- The model-facing schema contains fields the model owns. Session/Project identity, admission audit state, model assignment, and other runtime-derived fields remain hidden.
- Model-facing graph actions expose only `spec_path`; graph fields live in YAML so provider tool-call serialization cannot turn a nested graph into a string.
- Legacy YAML may be adapted at the file boundary without making legacy fields valid inline input.
- Runtime Admission and Workflow Authoring Check have separate names, state, and responsibilities.
- A rejected live replan or extend is parked by `DagControl.parkRejected`, which publishes durable `WorkflowPaused` only after the failed mutation released the workflow lock. If that pause fails or races with a terminal transition, the outcome reports the actual durable status (`parked`, `already-paused`, `terminal-unchanged`, or `failed`); callers must not assume the graph is parked.
- A compose graph is submitted like any other (#1158): the Workflow Authoring Check compiles it and the gate that refused it while the runtime could not expand a slot is gone, so `compose` is a block kind on the model-facing wire (`CompactBlock.kind` is the authoring kind list, not a copy of it). Compilation and validation run in full, and every defect of a composer is reported with its block or node and never found out at run time: a composer that is missing, not a composer or has nothing to expand into, a prompt asset, `fan_out` or `review` on a composer node, a reserved input alias. The engine's own marks `expand`, `join`, `compose_subtree` and `generated_helper` have no field in any model-writable schema (the wire, `NodeSchema`, `WorkflowBlock`, `StartSpec`, `ExtendSpec`, `ReplanSpec`); a replan can neither change nor clear them (`ReplanDefinition.changedEngineOwnedFields`), and a recovery points them at the attempts that now count (`planRecovery`).
- A compose slot is never spawned as authored. At admission, once its split node has settled, `DagComposeExpansion.expand` replaces it in one `Dag.extend` under the slot's fence (a stale fence means the parent reshaped the slot first, and its replan handler schedules the current graph); a nested slot is expanded the same way when its own split node settles. The join node it left is checked by `DagComposeExpansion.admitJoin` before it is spawned (Join Node). Cancelling the workflow ends the whole subtree, a slot cancelled before its split node settles is never expanded, and a `budget_exhausted` pause holds an expansion back without degrading it; none of this adds a control action.
- A compose expansion that did not follow its plan is coverage, in the same terms as a declined fan-out: the join node's `join.degraded` gives `compose expansion degraded: <reason>` on the join node, and each `join.items[].unsplit` gives `compose split declined: <reason>` on that item's node. A join node the admission check refused (`compose_required_missing`, `compose_no_results`) and a slot that failed (`compose_capacity`, `compose_unavailable`) are failed nodes, and the failed-node entry carries their error class and reason; coverage adds no second entry for them.
- `dag.compose.max_children`, `max_depth` and `max_subtree_nodes` are read from the global config layer only (`Config.dagGlobal`, never `DagSection`, which merges project values); a project file's `dag.compose` is stripped with one warning per file.
- The runtime fan-out extend fallback, the compose expansion and the recovery-pause adoption flow call `Dag` directly. They are engine-internal scheduling decisions, not caller control requests: they deliberately bypass `DagControl`, a declined fan-out expansion runs the writer serially without parking the workflow, and a compose expansion that cannot be made degrades to one fallback worker, or fails its slot with `compose_capacity`, the same way.
- A paused workflow gets one durable, delayed reminder per pause episode through the wake marker. A reminder never resumes, completes, or fails the workflow.
- Every terminal workflow is delivered to the parent session once. Failed and cancelled workflows, and completed workflows with a reporting checkpoint or without a delivered final answer (no delivery node, or a gate skipped it), are followed by one wake turn in either DAG mode. The one case the session's DAG mode decides (#1015) is a completed workflow whose only parent-visible output is an ordinary delivery leaf (`isDisplayOnlyCompletion` in `runtime/report-delivery.ts`): with the mode on, the report is delivered first and then one completion wake follows, so a staged plan never stops half way; with it off the report is displayed alone and the model gets no turn (#891). `DagDelivery` reads the durable `dag_mode` of the parent session at the moment of terminal delivery, so a switch made during a turn applies to the next delivery, and a failed read counts as off. A display acknowledges the delivery leaf's own wake together with the completion row. A running workflow whose current nodes have all reached a terminal status is waiting only for its completion check: it is neither a progress nor a stalled boundary, so the terminal wake is its only turn.
- Dependents of a reporting checkpoint must be gated on its output; authoring rejects ungated shapes at start/validate AND at replan/extend fragment actions, and the runtime replan/extend mutation seam re-checks the merged graph (exempting checkpoints already terminal in the durable graph — they are settled and immutable, the spawn-before-verdict race is past; runtime create remains deliberately unchanged). A gated checkpoint must declare `output_schema` (authoring obligation). An extend is authored against the live graph (#1073): blocks that depend on a Live Gate are gated by the compiler, a nodes fragment that leaves a dependent of a live checkpoint ungated is refused at authoring instead of at the runtime seam, with a `suggested_fragment` (node patches merged by id) only when the repair is simple: it edits the checkpoint and the nodes it gates, changes the meaning of no other node, and fails nothing on the rejected branch (every node a rejected verdict would skip, directly or by the scheduler's cascade, is already optional or `skip_ok`; otherwise the hint lists the nodes the caller must change), and a checkpoint that already settled is never gated, so the reopen-extend wave keeps working.
- A start document that declares `inputs` is always instantiated, with no inputs supplied as with some: a required input that is missing is an error, never a start from placeholders. Supplying inputs to a document that declares none is an error too, so a call never drops values it meant to use. Listing, reading, and template CI judge a template with sample values (`{ kind: "sample" }`) that follow the field they fill, so a constraint on an input's value is not read as a defect of the template; a curated template that declares inputs must start from `objective` alone.
- Workflow and node status vocabularies each have one source (`@graphagent/schema/dag-status`), and each contains exactly the statuses that durable events can produce. Terminal sets are domain-specific; `settled` means `completed` or `skipped` only, so an `aborted` node never counts as finished progress.
- A `budget_exhausted` pause is recorded on the durable event and read model, and only a resume/step transition lifts it. The public `Dag.resume` and `Dag.step` paths consult the injectable `ResumeGuard` policy (fail-open when no policy is provided) before publishing; internal terminalization through `failUnrecoverable` deliberately bypasses the guard. `DagControl` also prechecks the guard for paused `extend`, `replan`, `recover`, and `extend_timeout` before mutating; a veto returns a rejection without parking or mutation.
- Node cancellation is identified structurally by `error_class = "cancelled"` (never by matching `error_reason` text). A cancelled node lands on the `failed` status, is marked superseded, and therefore drops out of current-revision reads and agent-failure wake attribution.
- Wake attribution excludes cancelled rows (superseded) and `budget_exhausted` failures; both are engine outcomes, not agent failures, and must not trigger replan hints.

## Conventions

- Effective worker tool profiles are documented in [tool-profiles.md](docs/tool-profiles.md).
- DAG node attempts and task children of a DAG-on root are unattended: `question`/`plan_exit` are root-only, and `Permission.ask` routes every `ask: "auto"` pattern through `AskAdjudicator`/`SafetyGuard` after deny rules have won. A hit in the built-in safety list (SF-1..6, defined in [tool-profiles.md](docs/tool-profiles.md)) or in global `dag.safety.extra` (SX-n) becomes a tool error naming the rule and reason; a DAG node also records a durable `NodeSafetyDenied` on its `safety_denials`. The work continues, a user-written allow with a concrete pattern lifts SF-1..5 and SX-n (never SF-6), and every other ask auto-approves. The list is a guard against honest mistakes, not adversarial input, and is not a sandbox (see [No Sandbox](../../../../SECURITY.md#no-sandbox)): it judges structured facts only (tool, resolved paths, request metadata) and matches bash by literal pattern on a single simple command, never by interpreting its semantics. Node denials join coverage and the node/workflow wake counts; they never create a separate wake.
- `config.workspace` (and a node's `workspace` override) binds DAG children to an absolute linked worktree of the same project. Relative `spec_path` and draft paths still resolve from the calling session directory because the workspace is declared inside the spec. DAG settings (`dag.model` / `thinking_depth` in `<root>/.agents/settings.json`), prompt assets under `.agents/workflows/prompts`, the report area, snapshots and child tools resolve from the node's execution directory. Without `workspace`, children keep running in the owner/session directory, including non-git projects.
- `config.isolation: "worktree"` (#1030 D9-g) creates ONE workflow-level worktree at `dag.create` (deterministic name `dag-<dagID>-workflow`) and binds every child to it. It is start-only, mutually exclusive with `config.workspace`, and requires a clean git owner checkout. `Dag.create` creates the worktree before publishing any event (creation failure leaves zero durable trace) and persists the pointer as `config.worktree`; the WorkflowCreated event carries the worktree as `executionDirectory` and its fingerprint as `targetFingerprint`. Authoring rejects `isolation` in replan fragments, and `Dag.retarget` rejects isolated workflows.
- Workflow-level worktree settlement runs on the terminal transition in `DagLoop` BEFORE the wake nudge: completed commits pending work, writes a patch, and removes the directory with `keepBranch: true`; failed/cancelled commit + patch but keep directory and branch. A commit/patch/removal failure records `state: "kept"` with `reason`. `WorkflowWorktreeSettled` projects into `workflow.worktree` write-once and deliberately does NOT advance `seq`/`time_updated` (report identity and `completion_seq` are pinned to the terminal event). `settleWorkflowWorktree` is strictly idempotent so E1b (#1029 terminal branch) and a future process-level reconciler call the same seam.
- `workflow.worktree` settlement is the evidence consumers read: `workflow status` prefers the settled row over the live `config.worktree` pointer, and the final report/terminal wake append directory/branch/base/head/patch. A completed isolated workflow cannot be reopened by additive extend: its directory is gone while the kept branch remains, so `Dag._replan` rejects the reopen and directs the caller to a bounded successor workflow. Failed/cancelled workflows keep their worktree, so recovery remains valid.
- Known limitations of the workflow-level worktree (recorded, not silently handled): (1) a crash between `Worktree.create` and the WorkflowCreated publish leaves an unowned worktree on disk — the deterministic `dag-<dagID>-` name prefix is the handle for a future reconciler; (2) a host-level supervision sweep can terminalize a workflow without a loop entry, so settlement runs only when a terminal event handler observes it; a process-level reconciler must call `settleWorkflowWorktree` with an owner-instance provide; (3) deleting the parent session cascades the workflow rows without a terminal event, so its workflow worktree is left for that same reconciler; `DagLoop`'s SessionDeleted teardown deliberately does not settle.
- One user objective has at most one live DAG at a time; stage boundaries may start a successor after the previous one is terminal. Independent objectives may run concurrently; writers on the same workspace must be isolated or wait (engine-enforced, see DagControl). The one-live-DAG half is a modeling convention (issue #348) kept by orchestrator guidance (workflow-routing, the L2 stage text, and the `dag-auto`/`dag-recovery` skills), not by the engine: `dag.create` and the workflow tool's start accept a session with a live workflow, and the runtime tolerates a violation with bounded consequences (the wake model aggregates across workflows, and a goal is blocked by any DAG lease). The write half is engine-enforced because the plan block's disjoint-write-set discipline does NOT carry across workflows: the engine refuses the second unisolated writer in a workspace; see the write-safety invariant below.
- The workflow review gate (`config.review_gate`) and `config.acceptance` are fixed at `run.start`, and replan/extend fragments cannot change either. A session DAG mode of on or `mode: deep` fixes the gate to `strict`; `config.acceptance` supplies the completeness lane's items; review lanes expand from `lenses`/`skeptics` and default to the built-in read-only `auditor`.
- A review block's optional `prior_round` names a stored workflow review decision. The workflow tool resolves it before authoring into `prior_findings` (`<workflow_id>/<lane>/<index>`, with the prior disposition attached) and the compiler advances `review_round`; the authoring model never fills these by hand. The loader rejects a reference that is missing, foreign to the session, not completed, or already stopped.
- Every block review decision returns `dispositions` covering each lane `required_actions` entry regardless of verdict and `resolved` covering each prior finding. Entries are `{ node, index, novelty: "new" | { dup_of }, decision: "upheld" | "refuted", evidence }` and `{ ref, how: "fixed" | "refuted" | "still_open", evidence }`. Settlement rejects missing, repeated, malformed, and dangling entries. An ACCEPT additionally rejects an upheld action, a `still_open` resolution, and a `dup_of` address that is itself still open; under the strict gate it also requires every lens/skeptic lane to have completed.
- A review loop stops after five rounds or two consecutive rounds with no new upheld finding (`novelty: "new"` plus `decision: "upheld"`). The prior-round loader refuses a successor and the reason enters coverage; budget and node ceilings reject through their existing controls, never silently.
- The strict review gate requires block writers (`coding`/`prototype`, including a fan-out aggregator), a downstream `review.phase: "diff"` decision bound to each writer or its aggregator after verify, `required: true` and `skip_ok: false` decisions, `completeness` among the lenses, 1-50 unique `acceptance` ids when writers exist, and read-only lane/arbitration profiles (default `auditor`). Hand-authored write-capable nodes are rejected at authoring, validate, start, extend, and replan. `standard` reports the same gaps as warnings. A verify FAIL cannot be skipped into completion.
- Coverage is deterministic engine output. `DagCoverage.workflowCoverage` collects gated, aborted, and failed nodes, a declined fan-out (serial fallback), a degraded or unsplit compose expansion, a budget pause, lane `not_examined` gaps, unread result pages, safety denials, and review-loop stop reasons; `inspect` status/result exposes the list and delivery appends a language-titled section only when it is non-empty. Delivery nodes never author coverage prose; the parent's final report includes the section plus one `DAG usage` line.
- `WorkflowSummary.coverageCount` and `quality` (#1027 D6b) are derived by `DagSummaryDerived` from the same `DagCoverage.workflowCoverage` and `DagQuality` computations `inspect` runs, so the panel and the tool result agree on one fixture. `coverageCount` is the number of coverage entries for the workflow snapshot (result pages a reader stopped short of belong to one read and are not counted). `quality` is null unless the workflow is strict and holds a block review decision; its counters come from the arbitrated rounds only (a decision that has not completed is not a round). A workflow can hold several independent reviews, and a later round continues an earlier one through `prior_round` (a `prior_round` naming this workflow links two decisions into one chain; one naming another workflow starts a chain here). What is still open, how long a review has been quiet, and completeness are read from each chain's latest completed round and then combined: open findings add up, the quiet streak is the quietest chain's, and completeness is merged per acceptance item against the declared `config.acceptance` (an item is covered only when every chain's lane that judged it called it covered; an expectation several lanes listed counts once). `inspect` status shows the same counters as `review_quality`; the session DAG mode status combines them over the session's workflows. The derivation loads node outputs only where a computation reads them (`DagStore.getSummaryNodes`) and the publisher memoises it per workflow change marker (`DagStore.getWorkflowRevisions`), so usage ticks and finished workflows never re-parse configs.
- Write safety (#1031 M8) rests on one writer definition and runs before any durable write. (1) The `plan` agent may only run read-only nodes: `workflow start` and the `DagControl` extend, replan, and recover prechecks refuse a request whose newly-running nodes include a writer, without parking the workflow (draft, validate, resume, and step are not gated; writers that were already running keep running). The newly-running nodes are the extend fragment, a replan's added, restarted, and pending-or-queued replaced nodes (a re-stated running node keeps its run), and a recovery's replacement attempts (the selected nodes, their downstream, and work termination interrupted). A `debug` block's diagnosis node defaults to the write-capable `general` worker, so a plan-agent debug block must set `worker_type: explore`. (2) Two unisolated writers never share a workspace across live workflows: `workflow start` and the `DagControl` extend, replan, and recover prechecks look at every live workflow (pending, running, paused, or stepping, in any session; a paused workflow's pending writers count) and refuse, without parking, when one of its unfinished writers runs in the same canonical directory (`node.workspace`, else the workflow's execution directory, else its owner directory) as a writer the request would newly run (start: every writer of the graph; extend, replan, and recover: the same newly-running nodes as in (1), so a recovery's replacement attempts count too; retarget: the writers it moves into its target directory). A retarget adds no writer, so the plan gate does not apply to it, but it rebinds the execution directory, so the writers that spawn afterwards run in the target: the pending and queued nodes without their own `workspace`, plus the running target-sensitive nodes it restarts (`node_ids` narrows those). A running node it does not restart keeps running where it started, which is also where every check counts it (`NodeRow.directory`, else the execution directory). A retarget with no `workspace`, to the directory the workflow already runs in, of a terminal or workflow-isolated workflow, or with `node_ids` it would reject moves nothing here and is left to the real retarget. Node-level `isolation` and workflow-level isolation (a worktree is its own directory) never conflict, and a request with no unisolated writer, such as read-only work, never reads other workflows. A recovery re-runs the stored definitions and cannot add isolation, so its refusal tells the parent to wait for the other workflow; a retarget's refusal also offers a different linked worktree or a replan that isolates the moved writers. (3) A strict workflow (`review_gate: strict` or `mode: deep`) whose writers include an unordered pair, whose document binds no workspace or isolation anywhere, and whose directory is a clean git checkout with a commit starts with `config.isolation: "worktree"`; on a dirty, non-git, or commit-less directory it starts unisolated and the start result carries a warning telling the parent not to commit or stash on its own. The checks read state immediately before the durable write and take no cross-workflow lock, so two requests racing in the same instant can both pass.

## Boundaries

- `WorkflowAuthoring` owns source interpretation and authoring diagnostics.
- `DagWorkflows` owns saved-source discovery, scope precedence, and presentation metadata (including the one-line summary of a template's inputs); it does not decide startability. Its `builtin` scope always carries the four stage specs (`stage-understand`, `stage-design`, `stage-implement`, `stage-review`, in `builtin-workflows/`) that stage a multi-phase objective one workflow per stage, and adds the release snapshot of curated templates on top. A project or global file replaces a builtin of the same name, and a snapshot template replaces a stage spec. The stage specs are strict-gate templates the parent starts with `run.start { spec_path, inputs }` (`objective` is required; `stage-implement` and `stage-review` also take `acceptance`), and only `stage-implement` writes. Each ends in a reporting checkpoint that is not its delivery leaf (a review decision), so the parent gets a turn after every stage in either DAG mode: with the mode off, a workflow that ends in an ordinary delivery leaf is displayed without a parent turn (`isDisplayOnlyCompletion` in `runtime/report-delivery.ts`), and the parent could not read the result and start the next stage.
- `Dag` owns durable lifecycle invariants, event publication, and runtime transitions for already prepared graphs.
- `DagControl` owns the shared owner check, request-to-`Dag` mapping, rejection classification, paused-entry guard precheck, automatic resume after replan/extend, and post-failure parking; `Dag` remains the only lifecycle mutation authority.
- `DagDelivery` owns parent-facing delivery admission: the wake ledger read/ack path (admission equals delivery, #321), the agent-mailbox path (confirmed only by `associate`), the in-flight reservations, and the startup scan (the periodic fallback is the inbox tick). It registers with the shared per-instance `SessionInbox` as the `dag.delivery` source (priority 5, `idle_only`, claim = `deliver`) and the hint-only `dag.mailbox.step` step source. `DagLoop` does not subscribe to idle locally: it only wires event sources, which nudge delivery, and event sources never deliver inline.
- `DagMessages.changed` is a post-commit notification edge from the mailbox store to delivery. It carries no message body and grants no delivery authority; a missed, duplicated, or unsubscribed notification must fall back to the durable scan.
- `DagReviewLifecycle` owns verdict/arbitration consistency, round metrics, and the strict review-coverage diagnostics. The workflow tool resolves `prior_round` from stored outputs before authoring; the authoring boundary does not read workflow state itself.
- `DagCoverage` owns the deterministic coverage entries and the delivery section. It does not own safety policy: M7 denials join the same list instead of adding a second reporting path.
- `DagWriteGuard` owns the write-safety rules: the plan-agent gate, the `dag.permission: "readonly"` gate (#1324, which holds every caller, not only the `plan` agent), the cross-workflow write-conflict check, and the default-isolation decision. It is pure over facts the caller read, plus one store read of live workflows. `DagControl` and the workflow tool's start call it; it never mutates and never parks.
- Built-in DAG guidance belongs to the skill registry (`src/skill/builtin/`): six `dag-*` bodies own authoring, node, recovery, pattern, and policy contracts; `packages/core/src/plugin/command.ts` keeps only the always-on routing text. New guidance goes into the owning skill, not a command template.
- Provider/Agent/Skill/prompt catalogs own environment facts; the authoring boundary consumes current snapshots without becoming their source of truth.
- Release/config tooling invokes the same portable authoring boundary and adds repository compatibility and packaging gates.
